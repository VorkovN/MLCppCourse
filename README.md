Словарь терминов:

ML/инференс:

* Инференс — Процесс запуска обученной модели
* Execution provider — backend выполнения: CPU, CUDA, TensorRT, CoreML, DirectML, ROCm и т.д. Определяет, где и как
  выполняется модель
* Тензор — многомерный массив с типизированными данными и формой. В памяти обычно непрерывный блок (contiguous layout),
  но может быть strided.
* Shape / форма — размеры тензора по осям, например `[1, 3, 640, 640]` для батча из 1 изображения с 3 каналами 640×640.
* HWC/CHW — layout каналов изображения: Height-Width-Channel (OpenCV, numpy default) vs Channel-Height-Width (PyTorch,
  большинство моделей).
* NCHW/NHWC — layout батча: Batch-Channel-Height-Width (PyTorch, CUDA-оптимален) vs Batch-Height-Width-Channel (
  TensorFlow default, CPU-оптимален на Intel).
* Препроцессинг — приведение входных данных к формату модели: resize, color conversion, normalization, layout
  transformation. Несовпадение с обучением → деградация качества.
* Постпроцессинг — интерпретация выхода модели: NMS для детекций, argmax для классификации, denormalization координат,
  отрисовка результата.
* Нормализация — приведение значений к диапазону модели, обычно `(x - mean) / std` или `x / 255.0`. Mean/std должны
  совпадать с обучением (ImageNet: mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]).
* BGR/RGB — порядок цветовых каналов. OpenCV использует BGR, большинство моделей обучено на RGB. Перепутали → падение
  accuracy.
* Letterbox — resize с сохранением aspect ratio через padding. YOLO использует это, чтобы не искажать объекты. Важно
  сохранить scale/offset для обратного преобразования координат.
* Batch / батчинг — обработка нескольких входов за один forward pass. Увеличивает throughput (особенно на GPU), но
  добавляет latency (нужно накопить батч).
* Dynamic shapes — тензоры с переменными размерами (например, batch или resolution). Удобно для гибкости, но некоторые
  providers (TensorRT) требуют explicit profiles или работают медленнее.
* ABI - Application Binary Interface — «правила совместимости бинарников»: как устроены типы/исключения/линковка, какие
  версии компилятора и стандартной библиотеки совместимы между собой

Детекция/трекинг:

* Bounding box / bbox — прямоугольник объекта. Форматы: `xyxy` (x1,y1,x2,y2 углы), `xywh` (x,y,width,height от угла),
  `cxcywh` (center_x, center_y, width, height).
* Confidence — оценка уверенности модели (0..1 или 0..100). Используется для фильтрации: боксы с низким confidence
  отбрасываются.
* IoU (Intersection over Union) — метрика пересечения боксов: площадь пересечения / площадь объединения. Используется в
  NMS и для оценки качества детекции.
* NMS (Non-Maximum Suppression) — алгоритм подавления дублирующих детекций. Сортирует боксы по confidence, выбирает
  лучший, удаляет все с IoU > threshold. Реализации различаются (OpenCV, torchvision, кастомные) и дают разные
  результаты на граничных случаях.
* Landmarks — ключевые точки объекта (координаты характерных мест): углы глаз/рта для лица, суставы для pose estimation.
  Часто возвращаются в нормализованных координатах [0..1].
* FPS — frames per second, метрика производительности для realtime приложений. Включает весь пайплайн: захват кадра,
  препроцессинг, inference, постпроцессинг, отрисовку.

ONNX:

* ONNX — Open Neural Network Exchange, формат вычислительного графа. Включает ops (операции), tensors (данные),
  initializers (веса). Позволяет экспортировать модель из фреймворка и запустить в другом runtime.
* Opset — версия набора операций ONNX (opset 11, 13, 17 и т.д.). Более новые opset включают новые операции, но могут не
  поддерживаться старыми runtime.
* Кастомные операторы — ops, которых нет в стандартном ONNX. Требуют плагинов (shared library) для runtime или кастомной
  поддержки в execution provider.
* Graph optimization — оптимизации вычислительного графа runtime'ом: constant folding, operator fusion, layout
  transformation. ONNX Runtime имеет уровни: basic, extended, all (компромисс между скоростью загрузки и inference).
* Quantization — квантование модели (FP32 → INT8/FP16) для ускорения. Post-training quantization (PTQ) не требует
  обучения, quantization-aware training (QAT) даёт лучшее качество.

Сборка/зависимости:

* CMake — генератор build-системы. Описываете targets, dependencies, properties → CMake генерирует Ninja/Make/Xcode/VS
  проекты.
* Target — цель сборки (executable/library) с привязанными свойствами: sources, include dirs, compile/link flags,
  dependencies.
* `PUBLIC/PRIVATE/INTERFACE` — видимость свойств target: `PRIVATE` (только для текущей цели), `PUBLIC` (для цели и её
  потребителей), `INTERFACE` (только для потребителей, например header-only библиотеки).
* `find_package` — поиск и подключение внешней библиотеки. Ищет `<Package>Config.cmake` или `Find<Package>.cmake`,
  создаёт imported targets.
* Shared/Static библиотеки — динамическая (.so/.dylib/.dll) vs статическая (.a/.lib) линковка. Shared уменьшает размер
  бинарника и позволяет обновлять библиотеку отдельно, static упрощает deployment и избегает версионных конфликтов.
* rpath — runtime library search path, встроенный в бинарник. Указывает loader'у, где искать shared библиотеки.
  Неправильный rpath → "library not found" при запуске.
* ABI (Application Binary Interface) — совместимость на уровне бинарников: layout структур, name mangling, calling
  convention, exception handling. Смена компилятора/флагов/libstdc++ версии → ABI break → linker errors или runtime
  crashes.
* Toolchain — описание компилятора и окружения для CMake: компилятор, sysroot, флаги, пути поиска. Обеспечивает
  воспроизводимую сборку на разных машинах и в CI.
* Conan — пакетный менеджер для C++. Собирает/кэширует бинарники библиотек под конкретные настройки (profile): OS, arch,
  compiler, build type, options.
* Conan profile — описание build/host окружения: OS, arch, compiler, версия, stdlib, build_type. Определяет, какой
  вариант пакета использовать.
* Lock-файл (conan.lock) — фиксирует точные версии всех зависимостей (прямых и транзитивных). Гарантирует повторяемость
  сборки во времени.
* Транзитивные зависимости — зависимости зависимостей. OpenCV зависит от libjpeg, libpng, zlib и т.д. — они
  подтягиваются автоматически. Если версии не зафиксированы → конфликты/ABI breaks.

Python integration:

* Embedded Python — запуск CPython interpreter внутри C++ процесса через Python C API. Позволяет импортировать
  Python-модули и вызывать их из C++.
* Pybind11 — библиотека для биндингов C++↔Python. Упрощает создание Python-оберток для C++ кода и наоборот. Поддерживает
  embedded режим.
* GIL (Global Interpreter Lock) — mutex в CPython, который сериализует выполнение Python-кода. При вызовах из C++ нужно
  acquire/release GIL корректно, иначе deadlocks.
* venv / virtualenv — изолированное Python-окружение с собственными установленными пакетами. Для embedded Python нужно
  добавить `site-packages` venv в `sys.path`.

OCR:

* OCR (Optical Character Recognition) — распознавание текста на изображении. Пайплайн: предобработка → text detection →
  recognition → постобработка.
* Tesseract — open-source OCR движок на базе LSTM. Поддерживает 100+ языков, легко интегрируется, но чувствителен к
  качеству изображения.
* `*.traineddata` — языковые модели Tesseract (веса LSTM для конкретного языка). Можно комбинировать (`rus+eng`), но
  accuracy на границах языков может падать.
* PSM (Page Segmentation Mode) — алгоритм разбиения изображения на блоки/строки/слова. Примеры: PSM_SINGLE_LINE,
  PSM_AUTO, PSM_SPARSE. Неправильный PSM → неправильная сегментация → плохой результат.
* DPI — dots per inch, разрешение изображения. Tesseract оптимизирован для ~300 DPI. Низкое DPI (72-96) → мелкий шрифт
  распознаётся плохо, нужен upscale.

    * Начинаю курс с OpenCV, потому что на ее примере проще всего объяснить сборку и интеграцию.
      * Если мы говорим про сборку, то нельзя не упомянуть пару слов про CMake. CMake — это генератор build-системы: вы
        описываете цели (targets), зависимости и параметры сборки, а CMake генерирует проект для
        Ninja/Makefile/Xcode/Visual Studio. Аналоги: Meson, Bazel, QMake и т.п. Они отличаются философией и моделью

        простоту), но в индустрии CMake остаётся де-факто стандартом для C++ библиотек и большинство разработчиков
        используют только его. Примерно 80% всех проектов написано на Cmake. Потому вы можете комфортно чувствовать себя в
        С++ идустрии зная только эту систему сборки. Обычно все опенсорс библиотеки собираются симеком, потому для упрощения подключения библиотек рекомендую и в своем проекте всегда использовать его.
    * В большинстве «смузи»-языков используются пакетные менеджеры (pip, npm, cargo): ставишь зависимость одной
      командой, и она одинаково работает на машинах разработчиков/CI. В C++ всё сложнее из‑за компиляции и ABI, поэтому ценность пакетного менеджера ещё
      выше: он снимает боль с кроссплатформенной сборки, версий, флагов компилятора и повторяемости окружения.
    * Хоть в С++ пакетные менеджеры используются не так активно как в других языках, можно выделить один из самых популярных пакетных менеджеров — [Conan](https://docs.conan.io/2/). Он умеет собирать бинарники под разные
      ОС/архитектуры/компиляторы, фиксировать зависимости и отдавать их в CMake как нормальные цели. На примерах покажу
      базовую структуру профилей, как задаются опции/варианты (shared/static), и как в итоге «прилетают» зависимости в
      проект.
    * Почему это важно именно для ML: зачастую вы тащите не одну библиотеку, а несколько, например: opencv, onnxruntime, grpc. Каждая из них тянет еще несколько десятков библиотек в зависимостях, потому без порядка в управлении зависимостями проект быстро превращается в трудно поддерживаемый.

  Теория:
    * OpenCV: [OpenCV](https://opencv.org) (Open Source Computer Vision Library) — это open-source библиотека для компьютерного зрения и обработки изображений и видео. Основной язык библиотеки — C++, также доступны биндинги для Python, Java и других языков.
    * Библиотека разделена на несколько модулей:
      * `core` — фундамент библиотеки, базовый модуль, на котором построено всё остальное. Функционал: контейнер для изображений `cv::Mat`, базовые типы `Point`/`Size`/`Rect`/`Scalar`, операции над массивами, базовая математика.
      * `imgcodecs` — загрузка и сохранение изображений. Отвечает за работу с файлами изображений. Функционал: чтение изображений с диска, сохранение изображений в файл.
      * `highgui` — отображение и ввод. Модуль для работы с окнами и пользовательским вводом. Функционал: отображение изображений в окне, обработка нажатий клавиш и мыши.
      * `imgproc` — обработка изображений (ключевой модуль), основной модуль компьютерного зрения в OpenCV. Функционал: преобразования цветовых пространств BGR/Gray/HSV, фильтрация blur/Gaussian/median, пороговая обработка, морфологические операции erode/dilate, поиск контуров и форм, геометрические преобразования.
      * `videoio` — работа с видео и камерами. Отвечает за ввод и вывод видеоданных. Функционал: захват видео с камеры, чтение видеофайлов, запись видео.
      * `video` — анализ движения. Модуль для анализа изменений между кадрами. Функционал: трекинг объектов, оптический поток, анализ движения.
      * `features2d` — ключевые точки и дескрипторы. Работа с характерными точками изображения. Функционал: поиск ключевых точек, вычисление дескрипторов, сопоставление изображений.
      * `calib3d` — геометрия и камеры. Модуль для задач, связанных с 3D и геометрией. Функционал: калибровка камеры, коррекция дисторсии, работа с проекцией 3D→2D, оценка позы камеры.
      * `dnn` — нейросети. Модуль для инференса нейросетевых моделей. Функционал: загрузка моделей, выполнение инференса, поддержка CPU/OpenCL/CUDA (в зависимости от сборки). Поддерживаемые форматы: ONNX, TensorFlow, Caffe.
    * CMake:
      * CMake генерирует build-систему из декларативного описания. Вы пишете один `CMakeLists.txt`, он порождает Ninja/Make/Xcode-проекты под разные платформы. Два этапа: конфигурация (вычисление зависимостей, поиск библиотек) и сборка (компиляция/линковка).
      * Видимость зависимостей осуществляется через `PUBLIC/PRIVATE/INTERFACE` модификаторы. `PRIVATE` — только для текущей цели, `PUBLIC` — ещё и для тех, кто линкуется с вами, `INTERFACE` — только для потребителей (например, header-only библиотеки). Неправильная видимость ведет к раздутым зависимостям или отсутствию нужных include-путей.
      * Targets — центральная абстракция симейка: цели могут быть executable или library. add_executable() создает исполняемый файл с точкой вхожнеия main(), add_library() создается для подключения к разным executable целям. Другие цели (свои и внешние) можно найти через метод `find_package`. После вызова метода таргет только находится, чтобы слинковать эту цель с проектом необходимо подключить найденную цель в target_link_libraries
      * Cmake можно запускать с разными Build-типами (Debug/Release/RelWithDebInfo), они меняют оптимизации и отладочную информацию. Задать тип можно через через флаг передаваемый симеку: CMAKE_BUILD_TYPE, IDE при запуске передает этот флаг за вас. Важно: зависимости должны быть в совместимом типе, иначе ABI может сломаться. Conan, например, контролирует тип сборки и не будет предоставлять Release либы для Debug проекта и наоборот
      * Важно понимать, что CMake это только генератор build-системы. Вы описываете targets, dependencies, properties, CMake генерирует файлы Ninja/Make/Xcode/VS на ваш выбор. Конкретный генератор задается через опцию -G при запуске симейка. Make считается уже устаревшим, потому сейчас оптимальным вариантом считается Ninja.

    * Conan:
      * Conan управляет бинарниками библиотек под конкретные настройки: OS/arch/compiler/build_type/options. Конан описывает правила сборки библиотек и хранит бинарные файлы уже собранных библиотек чтобы во время ci не тратить ресурсы на повторную сборку. Conan довольно сложный и тяжелый инвструмент, хотя так может не показаться на первый взгляд.
      * Профили задают build/host contexts. Build — где собираем (компилятор, утилиты), host — где запускаем. При кросс-компиляции они разные (например, собираем на x86_64 Linux для ARM Android). Неправильный профиль ведет к линковке с несовместимым ABI или архитектурой.
      * Интеграция с CMake: Conan генерирует `conan_toolchain.cmake` и файлы с описанием пакетов. CMake подхватывает их через `include(${CMAKE_BINARY_DIR}/conan_toolchain.cmake)` и видит зависимости как `find_package`-цели. Никаких ручных путей — всё декларативно.
      * profile_linux_debug и profile_macos_debug описывают требования к системе (компилятора, ОС) на которой собираются библиотеки.
      * conanfile.txt описывает каие библиотеки нужно подключить. Какие теги и опции нужно использовать при сборке.
      * conan.lock фиксирует точные версии всех зависимостей (прямых и транзитивных). Без них версии библиотек «плывут» со временем. Conanfile.txt версионирует только теги библиотек, но иногда разработчики передвигают теги на другие коммиты. Иногда такое передвижение тега может сломать сборку, потому важно версионировать еще и хеш коммита. Фиксируйте профили и lock-файлы в git
      * Команду сборки через конан можно посмотреть в Cmake файле в теле execute_process(). Для удобства я вызываю конан из симейка, но сборку конан можно вызывать и через терминал.

* Mediapipe
  Темы урока:
    * Через Conan
    * Через Pybind
  Актуальность:
    * Частая прикладная задача — детектировать ключевые точки лица/рук/позы, чтобы считывать мимику (моргания, улыбку),
      позу, жесты и т.д. Но интеграция в C++ на практике выглядит как куча страданий.
  Теория:
    * MediaPipe: MediaPipe — это фреймворк от Google для построения real-time пайплайнов обработки медиа-данных (видео, изображения, аудио). В отличие от OpenCV, MediaPipe — это не просто набор алгоритмов, а система конвейеров (pipeline framework), где обработка данных идёт по заранее описанному графу.
    * Какие задачи решает MediaPipe: детекция и трекинг лица, детекция рук и жестов, определение позы тела (skeleton), face mesh (468+ точек лица), iris tracking, real-time трекинг на видео, mobile / web / desktop пайплайны. MediaPipe ориентирован на: реалтайм, стабильность трекинга, работу на слабых устройствах.
    * Основные компоненты MediaPipe:
      * Graph — граф обработки: Graph — это описание всего пайплайна (какие шаги выполняются, в каком порядке, какие данные передаются). Граф обычно описывается в `.pbtxt` файле. Пример логики графа получения лендмарков: получить кадр, детектор находит лицо, ограниченная область передаётся модели, модель считает ключевые точки, результат сглаживается, лендмарки выдаются пользователю.
      * Calculator — вычислительный узел: Calculator — это отдельный шаг обработки. Он может: принять данные, что-то посчитать, отдать результат дальше. Примеры calculator-ов: детекция лица, запуск нейросети, преобразование координат, фильтрация, трекинг. Calculator ≈ «одна функция в пайплайне».
      * Streams — потоки данных: Streams соединяют calculator-ы между собой. Через них передаются: изображения, тензоры, координаты, метаданные. Особенность: каждый поток привязан ко времени (timestamp), MediaPipe сам синхронизирует данные.
      * Packets — данные в потоках: Packet — это контейнер с данными. Он содержит: само значение, временную метку. Пример: кадр видео, список лендмарков, результат детекции.
    * Как MediaPipe работает внутри: MediaPipe почти всегда использует схему из двух этапов. Детекция (Detection): тяжёлая нейросеть, работает редко. Трекинг (Tracking): лёгкая модель или математика, работает на каждом кадре. Зачем это нужно: высокая скорость, стабильный FPS, экономия ресурсов.
    * Пример: Face Mesh: Детектор лица находит лицо, ограниченная область передаётся дальше, модель Face Mesh считает 468 точек, результат сглаживается, лендмарки выдаются пользователю. Всё это — один граф MediaPipe.
    * Готовые решения MediaPipe: MediaPipe предоставляет готовые пайплайны: Face Detection, Face Mesh, Hands, Pose, Holistic (лицо + руки + тело). Ты не пишешь алгоритмы, а используешь готовые графы.
    * Нейросети в MediaPipe: MediaPipe использует предобученные модели в формате TFLite, оптимизирован для mobile и real-time. Такие модели нельзя корректно сконвертироать в onnx потому что tflite сильно переужаты, потому при работе с медиапайп всегда приходится тащить зависимость от tflite.
    * Языки и платформы: MediaPipe поддерживает: C++, Python, JavaScript (Web), Android, iOS. Основная реализация — C++, биндинги поверх неё.
    * Pybind11: pybind11 — это C++ библиотека для создания Python-биндингов к C++ коду. Она позволяет передавать данные между C++ и Python. Из С++ можно напрямую вызывать код питона, главное только не забыть захватмть GIL, а из python можно вызывать с++ код как python библиотеку. Pybind11 часто используется, когда выжна производительность, например обработка входных и выходных данных для ML модели (C++), а бизнес логика нужна удобная лекого переписывающаяся (Python).
    * Ключевая идея pybind11: C++ остаётся C++, Python видит его как обычный модуль. pybind11 автоматически конвертирует типы, управляет временем жизни объектов, связывает классы, функции и структуры.
    * Как работает pybind11: В C++ описывается модуль, функции и классы явно экспортируются, код компилируется в `.so` / `.pyd`, Python импортирует модуль как обычный пакет.
    * Экспортировать через pybind11 можно практически все: функции, классы и методы, структуры и enum, STL-контейнеры, NumPy массивы.
    * Управление памятью в pybind11: pybind11 автоматически управляет reference counting, корректно связывает `std::shared_ptr`, предотвращает утечки памяти между C++ и Python.

* Yolo
  Темы урока:
    * Onnxruntime
    * Triton
  Актуальность:
    * YOLO — одна из самых популярных семейств моделей для детекции и сегментации. YOLO широко используется в: видеонаблюдении, автономных системах, робототехнике, промышленном зрении, аналитике видео
    * ONNX Runtime — универсальный рантайм для инференса. Как правило модели тренируют с использованием раздичный библиотек: Pytorch, TensorFlow, SiketLearn 

  Теория:
    * ONNX — это формат вычислительного графа: узлы (ops), рёбра (tensors), веса. Экспорт из PyTorch/TensorFlow не
      гарантирует запуск везде. Рантайм должен поддерживать все используемые операции и opset-версию. Кастомные
      операторы (например, NMS в самой модели) могут не работать без плагинов. Динамические формы (batch, resolution)
      удобны, но некоторые execution providers (например, TensorRT) требуют фиксированных размеров или explicit
      profiles.
    * ONNX Runtime — де-факто стандарт. Ключевые параметры: execution provider (CPU/CUDA/TensorRT/CoreML/DirectML),
      оптимизации графа (graph optimization level), количество intra/inter-op потоков. Неправильный provider → в 10-100
      раз медленнее. Неправильная форма тензора → segfault или garbage на выходе. Неправильный dtype (FP32 vs FP16) →
      либо не запустится, либо точность пострадает.
    * YOLO (база): YOLO (You Only Look Once) — это семейство нейросетевых моделей для детекции объектов, построенных по
      принципу one-stage detector. Основная идея YOLO — находить объекты на изображении за один проход нейросети, без
      отдельных этапов генерации кандидатов и их уточнения. Это делает YOLO быстрым, простым для интеграции и подходящим
      для real-time систем.
    * Какие задачи решает YOLO: Object Detection (поиск объектов: bounding boxes + классы), Instance Segmentation
      (детекция + маски объектов), Pose Estimation (ключевые точки, skeleton), OBB (Oriented Bounding Boxes — повёрнутые
      bounding box'ы), Real-time inference на CPU/GPU/edge-устройствах. В зависимости от версии и конфигурации, YOLO
      может поддерживать все или часть этих задач.
    * Ключевая идея YOLO: YOLO = «один взгляд на изображение». Вместо сложных многошаговых пайплайнов YOLO: получает
      изображение, выполняет один forward-pass, сразу предсказывает координаты объектов, классы, уверенность
      (confidence). Это позволяет минимизировать задержку, упростить архитектуру, повысить скорость инференса.
    * Как работает YOLO (упрощённо): Изображение → Backbone (извлечение признаков) → Neck (объединение признаков разных
      масштабов) → Head (предсказания) → Bounding boxes / классы / confidence.
    * Основные компоненты YOLO:
      * Backbone — извлечение признаков: извлекает из изображения информативные признаки (находит края и формы,
        выделяет текстуры, формирует многоуровневые представления). Backbone — это сверточная нейросеть, оптимизированная
        под баланс скорости и точности.
      * Neck — работа с масштабами: объединяет признаки с разных уровней, передаёт информацию между масштабами,
        улучшает детекцию мелких объектов. Часто реализуется через FPN/PAN-подобные архитектуры.
      * Head — предсказания: предсказывает координаты bounding box, определяет класс объекта, оценивает уверенность
        предсказания. В современных версиях YOLO часто используется anchor-free подход, упрощающий модель и ускоряющий
        обучение.
    * Формат выходных данных YOLO:
      * Object Detection: [x_center, y_center, width, height, confidence, class_id]
      * Segmentation: bounding box, class_id, бинарная маска объекта
      * Pose Estimation: bounding box, ключевые точки (x, y, score)
      * OBB: центр объекта, размеры, угол поворота
    * Инференс YOLO: при инференсе YOLO принимает изображение фиксированного размера, выполняет нормализацию, делает
      forward-pass, применяет NMS (Non-Max Suppression), возвращает финальные детекции.
    * Triton Inference Server: модель как микросервис с HTTP/gRPC API. Преимущества: версионирование (A/B тесты,
      rollback), dynamic batching (автоматическое объединение запросов для throughput), model ensemble (цепочка
      моделей), мониторинг (метрики latency/throughput). Недостатки: дополнительная латентность (network +
      serialization), нужна инфраструктура (docker, kubernetes). Для embedded/realtime — лучше in-process inference, для
      backend с множеством клиентов — Triton оправдан.

* OCR
  Темы урока:
    * Tesseract
  Актуальность:
    * OCR нужен, когда приходится «читать мир глазами»: мониторинг экрана ноутбука, текст с камеры/сканов, обработка
      пользовательских изображений, извлечение данных из документов, поиск по скриншотам и т.п. В C++ это часто
      встраивается в сервисы мониторинга/аналитики, где важна стабильность и воспроизводимость.
    * OCR кажется простой задачей («ну это же просто текст»), но на практике качество определяется предобработкой и
      доменом: скрин IDE, мемы, таблицы, терминал, чатик — это всё разные условия, и один и тот же движок будет вести
      себя по-разному.
  Теория:
    * OCR пайплайн: предобработка (contrast/denoise/binarization/deskew) → text detection (где текст) → recognition (что
      за символы) → постобработка (склейка строк, фильтрация, нормализация). Качество сильно зависит от домена: скан
      документа vs screenshot IDE vs фото таблички на улице — это разные условия (шрифты, разрешение, шум, угол).
    * Tesseract — классика для общего OCR. Основан на LSTM, работает прилично для чистых изображений (scans,
      screenshots), но чувствителен к качеству входа. Современные альтернативы (EasyOCR, PaddleOCR) на базе deep
      learning дают лучше accuracy, но тяжелее по зависимостям и сложнее в интеграции. Tesseract удобен тем, что легко
      подключается через Conan/vcpkg и имеет минимальные зависимости.
    * `*.traineddata` — это языковые модели. Tesseract поддерживает 100+ языков, но каждая модель добавляет overhead.
      Для смешанных языков (ru+en) указываете `"rus+eng"`, но accuracy может просесть на границах. Для production часто
      лучше отдельные модели для разных сценариев.
    * PSM (Page Segmentation Mode): задаёт, как Tesseract разбивает изображение на блоки/строки/слова. Примеры:
      PSM_SINGLE_LINE (одна строка), PSM_SINGLE_BLOCK (блок текста), PSM_AUTO (автоопределение). Неправильный PSM →
      неправильная сегментация → плохое распознавание. Если знаете структуру (например, один короткий текст без
      переносов), задавайте PSM явно.
    * Предобработка критична: `resize` до DPI 300+ (Tesseract ожидает ~300 DPI), `cvtColor` в grayscale, `threshold` (
      Otsu/adaptive), `morphologyEx` для удаления мелкого шума. Без этого на screenshot с retina-разрешением или
      низкоконтрастном изображении Tesseract выдаст мусор. Профилируйте на реальных данных: иногда простая binarization
      даёт +20% accuracy.
    * Confidence — это per-word метрика (0..100). Фильтрация по threshold (например, >60) убирает большую часть мусора.
      Дальше постобработка зависит от задачи: regex для поиска паттернов (email, числа, keywords), spell-checker для
      коррекции, словарь для валидации. Для классификации «работает/филонит» можно использовать bag-of-words и простые
      правила (IDE keywords vs соцсети keywords).

      работает/филонит.
